# 17 · Architecture & Design Review

> An internal design & architecture assessment of the RTS balance spec — answering the standing
> question: *is this well-structured and internally consistent, and where are the risks?*
> Read-only review; findings are **flagged, not patched**. Citations are `file:line` against the
> tree as reviewed. Verdicts were reproduced by running the scripts, not read off the prose.

**Headline:** the spec is unusually disciplined for its stage — a genuine data layer, four
verification scripts, and an honest split between "proven on paper" and "needs a build." The
architecture is sound in its bones. The risks are (1) a handful of **single-source violations that
have already drifted**, (2) two open balance flags that are **substantially model artifacts of a
combat sim that is weaker than the spec claims**, and (3) whole rule layers — most importantly the
dual-resource economy — that are **defined but neither implemented in the rosters nor verified by any
script**, which narrows what "certified" actually means.

---

## 1. Architecture soundness — the single-source design

The intended architecture is: **`data/*.json` is the source of truth; docs, lab, prototype, and
scripts all read it.** Where this is actually wired, it works well:

- `build-lab-data.mjs` and `build-prototype-data.mjs` inject roster JSON into the two HTML tools
  between markers, so the lab and prototype cannot drift from `data/units/*.json` as long as the
  build step is re-run.
- `matchup.mjs`, `composition.mjs`, `validate-roster.mjs`, and `certify.mjs` all read the roster
  JSON directly. No combat number is hand-copied into a script.

That is the right spine. But several facts still live in two places and **have already drifted**:

### 1a. The combat model and the curated mixes are duplicated, not shared
`prototype/index.html:120` literally comments *"curated combined-arms mixes — identical to
composition.mjs SUITES"* and re-lists them (`:122`), then re-implements `pdps`, `effHP`, and the
focus-fire `step` (`:135–157`) — a copy of `composition.mjs:17–49`. Two hand-kept copies of the same
model **will** diverge; a tweak to the sim's targeting or splash rule silently makes the
"visualizer of the balance sim" no longer match the sim. **Recommend:** extract one `combat-core.mjs`
module that both `composition.mjs` and the prototype import (the prototype can inline it at build
time via a marker, same pattern as the roster inject).

### 1b. Unit JSON is *part source, part generated artifact* — and this is unmarked
The roster files read as the source of truth, but several combat-critical fields are **generated by
heuristic scripts that overwrite the JSON in place**: `dmgType` (`add-dmgtype.mjs`), `range`/`aoe`/
`mobile` (`add-combat-stats.mjs`), and `resist`/`armor`/`ignoreResist` (`apply-armor.mjs`). The
first two *"only fill missing fields (hand-edits persist)"*, but `apply-armor.mjs` **overwrites
`resist` unconditionally** from `armor-table.json` (`apply-armor.mjs:14`). So a hand-tuned resist
survives until the next `apply-armor` run, then vanishes without warning. This is a real
single-source trap: `resist` is *derived* data (true source = `armor-table.json` + class), but it is
stored inline in the "source" file with no marker distinguishing it from truly-authored fields
(`cost`, `hp`, `dmg`, `build`). **Recommend:** either compute derived fields at load time instead of
persisting them, or namespace them (e.g. `_derived: {...}`) so nobody hand-edits a field the next
build will clobber.

### 1c. Human-facing tables are hand-maintained and already stale
The roster markdown tables in `design/12` and `design/13` are transcribed by hand from the JSON and
are **out of date** (see §2). Prose tables that restate machine data should be generated, or explicitly
labelled as illustrative with the JSON as canonical.

### 1d. The budget lives in four places
The Option-B budget appears in `data/factions.json`, `data/budget-options.json`
(`optionB_eightCategories_equal150`), `design/11-budget-options.md`, and `design/01-factions.md`.
Three agree; one (`design/01`) still shows the *rejected* pre-resolution table (§2). One canonical
home (`factions.json`) with the others linking to it would remove the drift surface.

## 3. The two open balance risks

### 3(a) Heavy-tank cost-efficiency (Vanguard / Marauder spam beats mixed armies)

**Both a real question and, as currently measured, mostly a model artifact — and the model artifact
dominates.**

The two sims flatly disagree about the exact interaction that decides this flag:

- **Duel sim** (`matchup.mjs`, with range + first-strike + kite): Missile Trooper **dominates**
  Vanguard — *89% force remaining* at 4000 cr, because the range-8 launcher gets a free first-strike
  window and kites the range-5 tank. Lancer→Vanguard: **61%**. By the duel model, anti-armor hard-
  counters tanks, exactly as designed.
- **Composition sim** (`composition.mjs`, no range/first-strike/kite): the default even-split
  Directorate mix **loses** to Vanguard spam (spam keeps 28%). Worse — and this is the diagnostic —
  a *missile-heavy* mix (2× Missile Trooper + Lancer + Howitzer) **loses harder** (Vanguard spam
  wins 50%). Doubling down on the unit the duel sim calls a 89% hard-counter makes you lose *more*
  in the composition sim.

That inversion is only explicable if the composition model is **structurally blind to the mechanic
that makes the counter work** — range/first-strike. Confirmed in code (C5): `composition.mjs` is pure
sustained-DPS + splash attrition; the durable tank simply out-attrites the fragile launcher when the
launcher is denied its range advantage. So the "heavy-tank" flag is **primarily an artifact of the
composition sim being a weaker engine than the duel sim**, compounded by the acknowledged pessimism
of the naive even-split baseline (`design/16` backlog #3).

There is a *residual* genuine question underneath: the Vanguard is cheap for its stat line (900 cr →
1600 hp + 120 antiArmor + aoe 2) and sits in the faction whose budget peaks are **durability 30 +
directCombat 26** (`factions.json`) — i.e. the tank *is* Directorate's budget. So a real cost-
efficiency concern is plausible; it is just **not what the composition sim is currently measuring.**

- **Cleanest fix:** unify the combat core (§1a) so `composition.mjs` inherits `matchup.mjs`'s range/
  first-strike/kite, then re-run. Only if the flag *survives* the richer model do a §8 cost pass on
  the Vanguard/Marauder (small cost-up or HP-down, per the §47 smallest-change order).
- **What would falsify "it's a model artifact":** with the unified model, run a first-strike-aware
  missile/Lancer mix vs Vanguard spam. If the mix now wins → it was the model (expected). If Vanguard
  spam *still* wins against a mix that gets its range advantage → it is a real balance bug and the
  cost pass is warranted.

### 3(b) Covenant utility anti-armor (hijack / mines / ambush invisible to a DPS sim)

**Predominantly a model limitation — cleaner-cut than 3(a) — with a real-but-separate playability
question it cannot answer either way.**

Three of Covenant's four anti-armor tools are **structurally unrepresentable** in any sustained-DPS
model: Hijacker (`dmg 0` — converts an enemy unit), Mine Layer (`dmg 0` — pre-placed area damage),
Ambush Tank (stealth first-strike from concealment). `composition.mjs` scores a `dmg 0` unit as pure
ablative HP, so it necessarily under-rates Covenant-vs-armor — the Marauder-spam flag (mix loses,
spam keeps 55%) is the sim mis-scoring its own inputs, not a measured imbalance. The docs already say
this; the review confirms it is correct and is the *dominant* effect.

The real question the sim can't reach: hijack, mines, and ambush are all **counterable by
information** — detection + escort neutralizes all three. So Covenant-vs-mass-armor could still be
genuinely weak *in practice* if a competent opponent always brings detection. A DPS sim can't see
that either — it needs playtest telemetry.

- **Cleanest fix:** stop trying to certify this matchup with the composition sim at all. Hijack/
  mines/ambush are binary/positional, not continuous DPS; **no attrition sim of any fidelity will
  score them honestly.** Mark Covenant-vs-armor **playtest-only** in the CHECKLIST rather than
  leaving a ⚠ that reads as a balance failure. A mechanic-aware sim (hijack = conversion, mine =
  pre-placed alpha, stealth = first-strike) is a large build; it is lower ROI than just playtesting
  the interaction.
- **What would falsify "it's a model limitation":** in playtest, a scouted Covenant mix (ambush +
  mines + hijack, detection contested) vs equal-cost Marauder spam. If the utility mix wins → model
  artifact (expected). If it still loses with utility fully and correctly used → Covenant has a real
  anti-armor hole and needs a roster answer, not a sim upgrade.

### Shared root cause
Both open risks trace to **one** thing: the composition sim is a pure sustained-DPS attrition model
that (a) omits the range/first-strike mechanics its sibling duel sim already has, and (b) cannot
represent `dmg 0` utility. **The single highest-leverage move for both flags is upgrading/unifying
the composition combat core** — it either resolves 3(a) outright or promotes it to a clean cost
question, and it lets 3(b) be honestly reclassified instead of flagged.

## 4. Coverage gaps (prioritized)

Relative to a shippable competitive RTS, given what is already covered:

1. **The dual-resource economy is defined but unimplemented and untested.** `resources.json` and
   `design/04` build the entire map-control / harassment / comeback loop on a **wood (floor) vs ore
   (ceiling)** contest, with named gatherers *Lumber Harvester (900)* and *Mining Vehicle (1400)*.
   **No faction roster contains either.** Each faction has a single generic harvester (Collector
   Truck 1400, Salvage Harvester 1200, Extractor Core 1600), and **no script reads `resources.json`.**
   So the headline economic system exists only in prose+data; the rosters and every sim are
   effectively single-resource. This is both a coverage gap and a latent inconsistency — reconcile
   the two-resource model with the rosters, or scope it down, before it is built two different ways.
2. **No economic verification at all.** `certify.mjs` proves coverage, anti-spam, and counter
   *presence* only. Payback (`cost / incomePerSec`) and the income curve are **provable on paper** —
   exactly the class the project claims it always proves — yet **`economy.json` is read by zero
   scripts.** A 20-line `certify-economy.mjs` would check that each harvester's payback lands in the
   §11 100–140 s band and that the income curve monotonically escalates. Its absence means "everything
   provable on paper is proven" is slightly overstated: it holds for *combat*, not economy.
3. **Whole rule layers are asserted but never exercised by any sim.** `combat-rules.json` (veterancy,
   upgrades, armor facing, repair, terrain) and `timings.json` (disables, stealth reveal, command
   capacity) are read by **no** verifier. The sims test base-stat attrition only. That is defensible
   for a paper spec, but the "20/20 gates" language should make explicit that the verified surface is
   *roster coverage + base-stat duels/compositions* — not economy, terrain, veterancy, upgrades,
   disables, or command capacity.
4. **Competitive maps** (already acknowledged) — `terrain.json` defines the §37 tests; no map files
   exist. Correctly a runtime gate.
5. **Cross-faction cost-efficiency band tuning** — the 5/12 out-of-band counters (C6) are a real,
   small piece of work; the sim over-produces "dominant" counters that the §8 table wants at
   "strong."
6. **Not addressed anywhere** (lower priority for a *balance* spec, but real for the game):
   controls/hotkeys/control-group UX, matchmaking/ladder/MMR (skill *tiers* are listed but no ranking
   system), audio design beyond telegraph cues, and netcode/determinism for the replay gate.

Priority: **P1** items 1–2 (they undercut the certification claim and risk divergent implementation);
**P2** items 3–6.

## 5. Faction identity integrity under Option-B (8 categories, equal 150)

The `≤3 sole-leads` rule is genuinely satisfied (D leads economy/combat/durability = 3; Cov leads
pressure/mobility/stealth = 3; Arr leads control/tech = 2), reproduced from `factions.json`. Identity
holds — but with two asymmetries worth naming:

- **Directorate is the "safely loaded" faction.** It owns the three categories that are *always*
  relevant — **economy 24, directCombat 26, durability 30** — while paying in situational ones
  (stealth 6, mobility 13). At equal 150, owning the three always-on axes makes it the strongest
  *default* pick, and this is not a coincidence with §3(a): the Vanguard (durability 30 + combat 26 in
  one unit) is precisely where that budget concentrates, which is why tank-spam is the thing the sim
  keeps flagging. Identity is intact and intended ("easy/durable"), but Directorate is the closest to
  overloaded and should be watched first in live win-rate data.
- **Array is the flattest — distinct by *mechanics*, not by *numbers*.** Its budget is
  18/12/20/20/20/14/26/20 — six of eight categories in the 18–26 band, second place in combat,
  durability, mobility, and economy. On the spreadsheet it reads as "competent everywhere," which is
  the mildest identity of the three. Its distinctiveness rests **entirely** on mechanics the budget
  doesn't capture — Warp Snare immobilization, shield/EMP counterplay, Disruptor shield-break. That
  is a legitimate design (the tech generalist), but it is the faction most at risk of feeling like
  "Directorate with shields" if those signature mechanics don't read strongly in-engine. Protect
  Array's identity in the *mechanics and readability* pass, not the budget.
- **Covenant is the sharpest and most correctly differentiated** (durability 10, combat 14, tech 11 —
  an unmistakable glass raider). The catch is that its identity *depends on* the utility anti-armor of
  §3(b), which is currently unverifiable. Covenant's identity integrity and open-risk 3(b) are the
  same problem viewed twice: the faction is only as distinct as its hijack/mines/ambush actually are
  in play.

Verdict: **three meaningfully distinct factions; nobody is bland by design.** The numeric risk is
Directorate-loaded-on-always-on-axes; the flavor risk is Array-reads-flat-without-its-mechanics.

## Prioritized recommendations

**P0 — do before trusting the balance numbers further**
- **P0.1** Unify the combat core: extract one shared model with range/first-strike/kite and have both
  `matchup.mjs` and `composition.mjs` (and the prototype) use it. Re-run the composition report. This
  directly addresses §3(a), reclassifies §3(b), and closes the C5 "same engine" inaccuracy. *(§1a, §3)*
- **P0.2** Fix the C1 stale budget in `design/01-factions.md` — it actively contradicts the canonical
  Option-B decision in the project's primary factions chapter. *(§2)*

**P1 — before handing to implementation**
- **P1.1** Regenerate or reconcile the roster tables in `design/12`/`design/13` (Rifleman 300/220,
  Raider 260/150) and the "45→46" count in `design/14`. Prefer *generating* these tables from JSON.
  *(§2 C2–C4)*
- **P1.2** Reconcile the dual-resource economy with the rosters, and add `certify-economy.mjs` to
  script-check payback/income against `economy.json`/`resources.json`. Closes the largest
  "claimed-but-unverified" gap. *(§4.1–4.2)*
- **P1.3** Deduplicate the curated mixes + combat model between `composition.mjs` and
  `prototype/index.html`. *(§1a)*
- **P1.4** Mark generated fields in the unit JSON (or compute them at load) so `apply-armor` can't
  silently clobber hand-tuning. *(§1b)*
- **P1.5** In the CHECKLIST, reclassify Covenant-vs-armor as **playtest-only** and note the 5
  out-of-band ("dominant") counters as an open §8 tuning item, so the 20/20 headline isn't read as
  "combat fully settled." *(§2 C6, §3b)*

**P2 — scope/quality**
- **P2.1** Add explicit "verified surface" language to CHECKLIST: coverage + base-stat combat only;
  economy/terrain/veterancy/upgrades/disables are asserted, not simulated. *(§4.3)*
- **P2.2** Pull the 5 out-of-band counters into the 25–45% band (small cost/DPS nudges), ideally with
  playtest data rather than more sim over-fitting. *(§2 C6)*
- **P2.3** One-line clarification of superweapon "activation" (charge time vs wall-clock) in
  `design/06`. *(§2)*
- **P2.4** Note the currently-unaddressed shippable-RTS areas (controls/UX, matchmaking/MMR, audio,
  netcode) as explicit out-of-scope-for-now rather than silent gaps. *(§4.6)*

## What I could be wrong about

- **The sim disagreement in §3(a) is my strongest claim, and it rests on the current code.** I
  reproduced Missile→Vanguard at 89% (duel) vs a missile-heavy mix *losing* to Vanguard spam
  (composition). If the intent is that the *composition* sim is the authority for army-scale
  questions and the duel sim is deliberately optimistic about range, then "the composition flag is a
  model artifact" is too strong — it might be the composition sim that is *right* (armies clump, first
  strike matters less at scale) and the duel sim that over-credits kiting. My recommendation (unify
  and re-measure) is robust either way, but which sim is "correct" is a design call I can't settle
  from the numbers alone.
- **I treat the roster-table drift (C2/C3) as pure documentation lag.** It is possible the docs
  reflect an *intended* value and the JSON nerf is the thing under reconsideration. Either way they
  must agree; I assumed JSON is canonical because the scripts and README say so.
- **Faction "flatness" for Array is a read of the budget spread, not of playtest feel.** A faction can
  have an even stat budget and still feel razor-distinct in the hands of a player because its
  mechanics dominate the experience. I'm flagging a *numeric* risk that may never surface as a
  *felt* one; only playtest can confirm whether Array reads as its own faction.
- **My "no script reads economy.json" finding is about the current tree.** If economic verification
  is intended to live in the lab's interactive validator rather than a headless script, then the
  "unverified" framing is partly unfair — though an interactive tool a human must open is weaker
  certification than a `certify.mjs` gate.
- **I did not exhaustively diff every prose number against every JSON value.** I spot-checked the
  units and values most load-bearing to the thesis (infantry nerf, budget, counts, the tank/missile
  interaction). Other small transcription drifts may exist beyond C2–C4.
